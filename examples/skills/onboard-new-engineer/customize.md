# Customizing this onboarding for your team

This skill is deliberately generic. Before you hand it to a new hire, replace
the placeholders below with your team's specifics. A generic onboarding doc that
still says "the architecture overview" instead of linking to it has not done its
job.

## Fill these in

**Access checklist** — the exact systems a new hire needs, with where to request
each:
- Code host: <org / repos>
- CI/CD: <system, where to find build status>
- Cloud / infra console: <which, what scope>
- Observability: <metrics, logs, tracing — links>
- Communication: <chat workspace, key channels to join>
- Ticketing / project tracking: <system, the team's board>
- Secrets / password manager: <how access is granted>

**The curated reading list** — three to five documents, linked, in order:
1. Architecture overview: <link>
2. How we work (branch / review / deploy): <link>
3. Local dev setup: <link>
4. <domain-specific doc>: <link>

**The starter task** — keep a small, real, low-risk task ready at all times so a
new hire never waits for one to be found. Where the team parks these: <label /
query / backlog link>.

**People to meet** — by role, with what each owns:
- Tech lead: <name / role>
- Eng manager: <name / role>
- Adjacent-system owners: <names / systems>

**On-call** — how the rotation works and how a new hire shadows it: <link /
process>.

## Keep it current

Review this customization whenever the toolchain, repos, or team change. The new
hire who finds a stale link is the signal that it needs updating — and the right
person to fix it.
